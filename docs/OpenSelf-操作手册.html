00

第一次：先存一份草稿

先熟悉操作，不需要调用 AI，也不需要向 GitHub 发布内容。

  1. 打开 OpenSelf 首页。如果尚未登录，点 用 GitHub 登录，按 GitHub 提示完成授权。成功标志：进入工作台，顶部出现“项目发现”“草稿队列”等入口。
  2. 打开 你的测试仓库页面，点 起草 Issue。
  3. 在 Issue 模板 中选择“空白 Issue”（如果提供），填写下面的练习标题和正文。若出现仓库表单，就按表单填写必填项。

练习内容，仅用于你自己的测试仓库；它不是一条真实缺陷报告。

标题：练习：测试 OpenSelf 草稿保存

正文：
这是一条用于熟悉 OpenSelf 的练习草稿。
我希望验证：填写内容后，可以在草稿队列中找到它。
本次练习只保存草稿，暂不发布。
  1. 点 预览 检查内容，再点 保存草稿。成功标志：出现“草稿已保存”，以及“查看草稿队列”链接。
  2. 点 查看草稿队列，找到刚才的标题。状态应为 待确认。
  3. 展开 预览；想改文字就点 编辑，改完再次保存。
到这里，第一次练习就完成了。
这份内容还在 OpenSelf 草稿里。等你确实想发到 GitHub，再按第 06 节操作。
01

先认识页面和术语

你会看到的词它是什么意思
仓库 / RepoGitHub 上的一个项目，通常写作“账号/项目名”。
Issue给项目提出问题、缺陷报告或功能建议，主要写文字。
PR / Pull request有人提交的一组代码改动，等待别人检查和合并。
Review / 审查针对 PR 的代码留下具体意见，以及“发表评论、批准 PR、请求修改”等结论。
草稿已经保存、等待你检查的内容。草稿本身不会出现在 GitHub。
API Key让 OpenSelf 调用你的 DeepSeek 账户的密钥。它不是 GitHub 密码。
顶部入口什么时候用
工作台上方“我的仓库”显示当前 GitHub 账号名下的项目，点击直接进入 PR 列表。下方还有“待我审查”“我的 PR”、草稿数量和贡献雷达。
项目发现搜索你感兴趣的项目，然后查看说明、Issues 和 Pull requests。
AI 贡献描述想法寻找项目，扫描公开仓库，再生成 Issue 或代码改动与 PR 草稿。
草稿队列预览、编辑、丢弃草稿，或确认向 GitHub 发布。
发布记录查看已经成功发布的记录，再跳转 GitHub 核对。
账号设置配置个人 Key、审查风格、学习模式、私有仓库权限等。
02

配置自己的 API Key

你的账号已经配置好；下面这段可以给以后使用项目的人看。当前版本的个人 Key 输入框用于 DeepSeek API Key。

  1. 在 DeepSeek 官方开放平台获取自己的 API Key。入口可从 DeepSeek 官方“首次调用 API”文档进入。
  2. 登录 OpenSelf，进入 账号设置，找到 AI 与审查设置。
  3. 把 Key 粘贴到 自己的 DeepSeek API Key 输入框，点它下方的 保存。
  4. 看到“已保存，末四位：……”以及“当前使用你自己的 API Key，其他账号无法使用。”就说明已保存。输入框清空是正常现象。保存只确认密钥已存入，是否有效还要以实际 AI 调用结果为准。

每个账号只使用自己的 Key。没填、删除或 Key 失效时，不会改用项目所有者的 Key。手动浏览项目、写 Issue 和审查 PR 不需要 AI Key。

要更换：输入新 Key 后保存。要停止使用：点 删除 Key。这里删除的是 OpenSelf 保存的副本；如需让该 Key 在所有应用中作废，应到 DeepSeek 平台撤销。

Key 加密保存在这个 OpenSelf 实例的服务器中，页面只显示末四位。请在 Key 输入框填写，不要把它写进 Issue、PR 评论或聊天。

03

找到 GitHub 项目

自己的仓库，直接从工作台打开。
进入工作台，在“我的仓库”中点击项目卡片上的“查看 PR”，就能看到该仓库的 Pull requests。新建仓库后可点“刷新仓库”；仓库较多时可点“显示更多仓库”。私有仓库需先在账号设置中启用访问权限。

要找其他人的项目，再使用下面的项目发现流程：

  1. 点顶部 项目发现。
  2. 输入关键词，或直接输入 qilin-ljl/linli-share。输入后稍等，结果会自动出现，无需找“搜索”按钮。
  3. 点结果中的仓库名称，进入详情页。
  4. 先看 概览 里的 README 和贡献指南，再选择 Issues 或 Pull requests。

Issues 列表里的标题会打开对应 GitHub 讨论；Pull requests 列表里的标题会进入 OpenSelf 的代码审查页面。列表可切换“开放 / 已关闭”。

找不到刚创建的仓库时，可先使用本手册的 测试仓库直达链接。

04

写一条 Issue

入口：项目详情页右上方 起草 Issue。在动笔前，先看一下已有 Issues，避免重复提出同一个问题。

自己写

  1. 先选 Issue 模板，再填写。切换模板会重置部分内容。
  2. 填写标题；正文写清“做了什么、期望什么、实际发生什么”。表单模板按字段填，并完成必填项。
  3. 点 预览 检查，再点 保存草稿。
  4. 进入 草稿队列 进行最后检查。

让 AI 帮你整理

  1. 先确认个人 Key 已保存，并选好 Issue 模板。
  2. 在 Issue 助手 → 描述你遇到的问题 中填写真实情况。
  3. 可先点 检查重复 Issue，阅读相关讨论。
  4. 选择输出语言，点 AI 起草，等待结果。
  5. 核实内容后点 填入编辑器，再检查必填项并保存草稿。

描述问题时可参考这个格式，把内容换成你实际遇到的情况：

使用环境：系统、软件版本、浏览器等。
复现步骤：第 1 步……第 2 步……
预期结果：我希望看到什么。
实际结果：实际看到什么，以及具体报错。
补充材料：与问题有关的日志或截图说明。
AI 助手中的按钮作用与下一步
检查重复 Issue显示可能相关的讨论。请打开看实际内容；“未找到重复候选”只代表当前搜索范围的结果。
AI 起草生成建议文字。若出现“还需要补充的信息”，补完后再次起草；AI 结果还没有填入你的最终草稿。
填入编辑器把 AI 结果放进下方标题、正文或表单，可能替换你原先填写的内容。之后还需要保存草稿。
检查质量检查当前编辑器中的正文，给出评分和补充建议。只有已有正文时才能使用。
翻译草稿生成当前正文的译文；检查后点“使用译文”。表单模板的整篇译文不能直接回填，需要按字段处理。

“跟随仓库语言”用于自动选择起草语言。翻译时如果保留该选项，中文界面会默认译成英文、英文界面默认译成中文；需要确定方向时，直接选“中文”或“英文”。

离开页面前请保存草稿。
正在输入的内容并非自动保存；AI 起草、预览、填入编辑器，也都不会直接发布。
05

审查一份 PR

自己的项目：工作台 → 我的仓库 → 点击仓库 → 点一条 PR，打开审查页后可点“开始预审”。其他项目可以从项目发现进入，再选择 Pull requests。“待我审查”只显示明确邀请你审查的 PR；仓库的 PR 列表不要求这份邀请。

先看懂代码页面

左侧“改动文件”列出这次修改的文件。点文件后，中间显示代码差异。“分栏”是左右对照，“统一”是合在一起显示；“LEFT”指旧代码，“RIGHT”指新代码。

自己写审查意见

  1. 阅读 PR 说明，查看改动文件和检查结果。检查结果无法访问时，不能据此判断检查已经通过。
  2. 选中一个文件，点代码行旁的加号；也可在下方填写 行号 和 代码版本。
  3. 在 审查意见 中说明具体问题、触发条件和影响，点 添加行内评论。成功标志：页面下方“X 条行内评论”区域出现这条评论。它还没有发布。
  4. 填写 总评，选择 审查结论，点 生成审查草稿。
  5. 进入草稿队列，按第 06 节检查和发布。
审查结论含义
发表评论提交讨论或建议。第一次练习可以使用这个选项。
批准 PR向 GitHub 提交“认可这份改动”的审查结论。合并代码仍需在 GitHub 单独操作。
请求修改说明哪些问题需要修正，再进行后续审查。

自己创建的 PR 只能选“发表评论”，不能批准自己或向自己请求修改。

让 AI 预审，再由你决定采用哪些意见

  1. 在 AI 预审 中选择“安全、性能、可读性、测试”等审查重点，至少保留一项。
  2. 点 开始预审，等待分析进度。首次使用先关闭“学习模式”，可以直接看到结果。
  3. 逐条核对代码：合理的点 接受，需要改写的点 编辑意见，不适用的点 拒绝。
  4. 点 将已接受意见加入草稿，把接受或编辑后的意见加入当前审查内容。
  5. 补充总评和审查结论，再点 生成审查草稿。要到草稿队列里看到这份草稿，才算完成保存。
AI 的“接受”和审查结论“批准 PR”是两个不同操作。
接受只是选中一条建议。最终审查结论和发布内容仍由你决定。AI 没找到问题时，也要查看它深入审查了多少文件、跳过了哪些文件。

如果 PR 在你审查期间又有新提交，系统会提示版本已改变。重新打开或刷新 PR、检查最新改动后，再生成草稿。

06

检查草稿并发布

1. 编辑 / AI 起草准备文字和意见
2. 保存 / 生成草稿存入 OpenSelf
3. 预览 / 修改核对目标与内容
4. 批准并发布确认后发往 GitHub
  1. 打开 草稿队列，找到对应草稿，确认仓库名和 PR 编号是否正确。
  2. 展开 预览。Issue 检查标题和正文；PR 审查还要检查行内评论、代码版本和审查结论。需要改动就点“编辑”，再保存。
  3. 确实要发布时，点 批准并发布，阅读弹窗中的仓库名称并确认。选择“批准 PR”或“请求修改”时，还会再次确认审查结论。
  4. 等待后台发布，状态变成 已发布 后，点 在 GitHub 查看 核对结果。也可以到“发布记录”查找。
草稿状态你可以怎么做
待确认预览、编辑、丢弃，或批准并发布。
已批准 / 发布中已交给后台处理，等待结果。此时不要重复新建同样内容去发布。
已发布通过“在 GitHub 查看”核对；OpenSelf 不提供对已发布内容的本地撤回按钮。
发布失败先读错误提示。普通可修正的错误可编辑后保存，再批准；结果未知的情况按下方说明处理。
已丢弃这份草稿不再进入发布流程。
遇到“发布结果尚未确认”时，先去 GitHub 检查。
可能请求已经送达，但结果没有返回。不要立刻新建并重发；先确认有没有重复内容，必要时让维护者核查。

本地版不限制指定仓库。GitHub 仍可能因权限、仓库关闭 Issues、归档或其他仓库规则而拒绝操作；私有仓库需先启用访问权限。旧版因测试仓库限制而失败的草稿，可编辑并保存后再确认发布。

07

其他设置和贡献雷达

  • 审查风格：在设置里写下偏好，例如“优先关注逻辑错误和缺少的测试，意见简洁，给出复现条件”，然后点该区域的“保存”。“重新学习风格”会使用你可访问的历史审查，需有个人 Key。
  • 学习模式：先隐藏 AI 结果，让你自己记录意见；点“对比我的意见与 AI”后再查看。新手想直接看到 AI 结果，可以先关闭。
  • 每个 PR 最多显示的意见数：可选 10 或 20。这控制展示数量，不代表已覆盖全部代码问题。
  • 私有仓库：点“启用私有仓库”后，按 GitHub 提示重新授权。使用私有仓库 AI 时，还需确认将相关内容发送给 DeepSeek。
  • 使用统计：查看每天预审、起草、发布次数和模型 token 用量；实际费用以你的 DeepSeek 账户为准。
  • 贡献雷达：在工作台推荐与你常用语言有关的公开入门任务。新账号、没有相关仓库或没有匹配结果时，列表可能为空；它不会自动替你领取任务或发布内容。

平时离开只需退出登录。“撤销 GitHub 授权”会删除本实例保存的 GitHub 令牌、个人 Key 和登录会话，已有草稿仍保留；它不等同于删除全部账号数据。

08

浏览器插件（可选）

先把网页版用熟即可。插件让你在 GitHub 页面旁边打开 OpenSelf 侧边栏，仍需本地网站和后台服务运行，也使用当前账号自己的 Key。

需要插件时，再展开安装步骤
  1. 打开 Chrome 扩展管理页 chrome://extensions，或 Edge 扩展管理页 edge://extensions，开启“开发者模式”。这两个地址请复制到浏览器地址栏。
  2. 选择“加载已解压的扩展程序”。Chrome 选择下面的 chrome-mv3 文件夹；Edge 选择 edge-mv3 文件夹。
C:\Users\pc\Desktop\githubpr\apps\extension\.output\chrome-mv3
C:\Users\pc\Desktop\githubpr\apps\extension\.output\edge-mv3
  1. 复制插件 ID，由维护者填入项目根目录 .env 的 EXTENSION_IDS，多个 ID 用英文逗号分隔，然后重启网站。第一次可把插件 ID 告诉我协助配置；不要发送 API Key。
  2. 点击插件图标打开侧边栏，点“连接 OpenSelf”，按提示登录。
  3. 打开 GitHub PR 或新建 Issue 页面，使用侧边栏的预审、草稿和回填功能。

插件里的 填入 GitHub 页面 只把文字放进 GitHub 输入框；要发布仍需你在 GitHub 点击提交。若无法回填，会尝试复制到剪贴板，让你手动粘贴。

当前插件通过本地文件夹安装，尚未发布到扩展商店。默认安装包连接 localhost，只适用于本机测试。

09

下次怎么打开

推荐：双击本地启动文件。
先打开 Docker Desktop，再到 C:\Users\pc\Desktop\githubpr 双击 Start-OpenSelf.cmd。它会启动数据库、网站和后台，也会处理本机普通 PowerShell 找不到 pnpm 的情况。使用时保留窗口；更新后先关闭旧的启动窗口再启动。

如果电脑和服务一直开着，直接打开 http://localhost:3000/zh 即可。电脑重启后，需要先把服务启动。

电脑重启后的启动步骤
  1. 打开 Docker Desktop，等待它显示引擎已运行。
  2. 打开 Windows PowerShell，依次粘贴并执行下面三行。最后一行会持续运行，使用网站时保留这个窗口。
cd C:\Users\pc\Desktop\githubpr
docker compose up -d
pnpm dev

看到网站启动提示后，打开 OpenSelf 首页。这里的 pnpm dev 会一起启动网页和后台任务。

数据库已初始化，不用每次重新安装依赖或重新填写 OAuth。只有项目更新包含数据库变更时，才按维护说明执行迁移。

用完后怎么关

在运行 pnpm dev 的 PowerShell 窗口按 Ctrl + C 可停止网站和后台任务。需要停止数据库时，在项目目录执行 docker compose stop，它会保留数据库内容。

如果是我帮你在后台启动的服务，可直接让我停止。不要为了关网站去删除 Docker 数据卷。

把 localhost 链接发给别人，他们不能访问你的这台电脑。
localhost 代表访问者自己的电脑。要让其他人直接登录使用，需要把项目部署到可访问的网站地址；他们再登录各自的 GitHub、填写各自的 API Key。
10

常见问题

我不会写代码，也能用吗？

可以先用项目浏览和 Issue 功能，把问题讲清楚即可。PR 审查涉及代码，AI 可以协助解释和发现线索；只发布你理解并核实过的意见。

页面提示“无法访问此网站”

先确认 Docker Desktop 正在运行，网站启动窗口没有关闭。按第 09 节重新启动。若提示 3000 端口已被使用，先打开首页检查是否已有服务，不要重复启动很多个窗口。

PowerShell 提示找不到 docker 或 pnpm

优先双击项目根目录的 Start-OpenSelf.cmd，它会寻找常见安装路径以及本机开发工具中的 pnpm。如果启动文件也报错，把错误文字发给我处理，不需要重新申请 GitHub 账号或 API Key。

我已经登录 GitHub，为什么 OpenSelf 还让我登录？

GitHub 网站登录和 OpenSelf 授权是两步。请从 OpenSelf 首页点击“用 GitHub 登录”；成功后会回到本地工作台。若一直显示登录失败，检查本地服务是否启动，并让维护者核对 OAuth 配置。

点 AI 按钮后提示先配置 Key

到“账号设置 → AI 与审查设置”保存当前账号自己的 DeepSeek API Key。别的用户已经配置好，不代表你的账号也配置好了。

Key 保存了，却提示无效或模型服务不可用

“已保存”只表示存入成功。确认使用的是 DeepSeek API Key、复制是否完整、账户是否可用，再重试。模型网络或服务故障也可能导致不可用；不需要反复新建相同任务。

AI 一直处理，或者草稿一直显示“已批准”

先给任务一些处理时间。持续不变化时，确认后台 Worker 正在运行；按第 09 节启动的 pnpm dev 会同时运行它。需要诊断时，在另一个项目终端执行 pnpm worker:ping，成功应显示 ok: true。

可以向别人的项目提 Issue 或提交审查吗？

可以。通过“项目发现”打开对应仓库，准备 Issue 或已有 PR 的审查草稿，再确认发布。当前本地版已移除测试仓库限制，具体操作仍需符合 GitHub 权限和仓库规则。

能直接修改代码并创建新的 PR 吗？

可以。打开“AI 贡献”，体检公开仓库，在一条候选发现下点“准备代码改动”。检查差异并保存 PR 草稿，再到草稿队列确认。OpenSelf 会创建独立分支，必要时先 fork，然后提交 PR；不会自动合并。详见第 11 节。

为什么没有“起草 Issue”按钮？

先等仓库资料加载完成。仓库已归档或没有开启 Issues 时，不会显示可用的起草入口；可以点“在 GitHub 查看”核对项目状态。

为什么找不到 PR，或看不到代码差异？

先确认项目确实有 PR，并检查“开放 / 已关闭”筛选。没有文本差异可能是二进制文件或内容过大；系统会提示，必要时到 GitHub 查看原始改动。

我点了“接受”，为什么草稿队列没有东西？

接受只选中一条 AI 建议。还需要点“将已接受意见加入草稿”，填写总评和结论，再点“生成审查草稿”。

发布失败后，怎么再次发布？

先读原因。对于普通内容或模板错误，点“编辑”，修正后保存，让状态回到“待确认”，再批准。若提示“发布结果尚未确认”，先到 GitHub 核实，避免重复。

为什么设置中还看到 platform.aux 等旧记录？

这是切换为个人 Key 模式之前保留的历史用量。现在的新 AI 任务只使用当前账号的个人 Key，历史记录不会开启共享 Key。

11

AI 找项目、体检与创建 PR

先在账号设置保存自己的 API Key，再打开顶部 AI 贡献。查找、分析和生成改动会使用你的模型账户额度。

有一个想法，先找合适的项目

  1. 在 描述你的想法 中说明想做什么、熟悉的语言和希望改进的方向。例如：“想给 TypeScript 命令行工具补充输入校验和测试，找一个规模适中、还在维护的项目。”
  2. 点 寻找项目。AI 会整理搜索条件，读取真实 GitHub 仓库信息和 README，再给出匹配理由与贡献方向。没有匹配结果也可能是正常结果。
  3. 查看项目卡片；选择一个感兴趣的仓库，点 体检这个仓库。推荐并不保证维护者会接受某个 PR，先阅读项目的贡献规则。

已经知道仓库，直接体检

  1. 在 AI 贡献页面输入公开仓库的 GitHub 链接或“账号/仓库名”；也可以从仓库页面点击 AI 体检。
  2. 填写可选的检查重点，选择文件数量，点 开始体检。默认最多分析 20 个文件；较大的范围会花更长时间并消耗更多额度。
  3. 先看覆盖范围和跳过原因，再阅读候选问题的文件、行号、代码证据、修改建议与验证步骤。点击代码链接可查看扫描时的确切版本。
  4. 想提文字建议，点 用此发现起草 Issue，继续按仓库模板填写、检查并保存草稿。候选的证据会带入描述，不会直接发布。

让 AI 生成改动，再提交新的 PR

  1. 在体检结果中选定一条候选；可补充修改要求，再点 准备代码改动。
  2. 进入 代码改动预览，逐项查看增加、删除的内容以及建议测试步骤。此时还没有创建 GitHub 分支。
  3. 编辑 PR 标题和正文。默认勾选 以草稿 PR 创建，方便后续验证；点 保存 PR 草稿。
  4. 进入草稿队列，展开预览，确认仓库、基准版本和完整差异后，点 批准并发布 并确认弹窗。系统才会写入 GitHub。
  5. 有目标仓库写权限时，系统在该仓库创建独立分支；没有写权限时，先在你的账号下复用或创建 fork，再从分支向原仓库提交 PR。成功后点“在 GitHub 查看”。
体检范围与验证状态会明确显示。
当前仅支持公开仓库；每文件最多分析前 400 行、16,000 字符，总计最多 160,000 字符。生成改动最多 5 个文件，跳过密钥、工作流、二进制和生成内容。系统不会执行目标仓库代码或测试，候选并不等于已证实的缺陷；按给出的步骤验证后，再决定是否发布或转为正式 PR。

模型输出校验失败时，系统会只对这一批文件使用快速模式补救。仍失败的文件会标注“未完成分析”，其他有效结果会保留；报告会明确提示“不完整”，不代表这些文件没有问题。切换页面不会取消后台任务，可通过原任务地址返回；重复点击“开始体检”会创建新任务并产生新的模型用量。

如果提示仓库版本已变化，请重新体检并生成改动；如果自己的同名仓库并非目标仓库的 fork，系统会提示冲突。发布途中出现“结果尚未确认”时，可能已创建 fork 或分支，先去 GitHub 核实再处理，避免重复提交。OpenSelf 不会自动合并 PR。

适用范围：OpenSelf v0.2 桌面本地版，个人 API Key 模式。页面按钮与当前项目实现对应；不需要先安装浏览器插件，也不需要手机端。
